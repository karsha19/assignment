# API Workflows

Full interactive API documentation is auto-generated by FastAPI and served
at `http://localhost:8000/docs` (Swagger UI) and `/redoc` once the backend
is running.

## Authentication

```
POST /api/v1/auth/login
{ "username": "admin", "password": "Admin@12345" }
→ { "access_token": "...", "token_type": "bearer", "role": "admin", "username": "admin" }
```

Include the token on every subsequent request: `Authorization: Bearer <token>`.

## Core demonstration workflow

1. **Login as admin.**
2. **Add two cameras**
   ```
   POST /api/v1/cameras
   { "camera_code": "C001", "name": "Ahmedabad Traffic Junction",
     "department": "Traffic Police", "zone": "Zone-1",
     "latitude": 23.0225, "longitude": 72.5714,
     "source_protocol": "recorded",
     "stream_reference": "/media/sample/c001_traffic_junction.mp4" }
   ```
3. **Add a watchlist record**
   ```
   POST /api/v1/watchlist
   { "entity_type": "stolen_vehicle", "identifier": "GJ01XX0001",
     "display_name": "Stolen vehicle - demo", "reason": "Reported stolen (synthetic)" }
   ```
4. **Submit a matching analytics event** (this is the single request that
   validates, persists, correlates, and alerts — see `docs/architecture.md`
   §2 for the full internal sequence):
   ```
   POST /api/v1/analytics/events
   { "idempotency_key": "demo-evt-1", "camera_id": "<camera id from step 2>",
     "event_type": "anpr", "entity_identifier": "GJ01XX0001",
     "confidence": 0.94, "vehicle_type": "sedan",
     "event_timestamp": "2026-09-17T10:02:00" }
   ```
   Response is `201` with the persisted event. A connected WebSocket client
   receives `analytics_event`, then `watchlist_match` and `new_alert`.
5. **List alerts and acknowledge/resolve**
   ```
   GET /api/v1/alerts?status=new
   POST /api/v1/alerts/{alert_id}/acknowledge
   POST /api/v1/alerts/{alert_id}/resolve
   ```
6. **Search movement history**
   ```
   GET /api/v1/entities/GJ01XX0001/movement-history
   → { "identifier": "GJ01XX0001", "normalized_identifier": "GJ01XX0001",
       "events": [ { "camera_id": "...", "camera_name": "...", "latitude": ...,
                     "longitude": ..., "timestamp": "...", "confidence": 0.94,
                     "event_type": "anpr" }, ... ] }
   ```
7. **Audit trail**
   ```
   GET /api/v1/audit-logs
   ```

## Idempotency and duplicate handling

Every analytics event requires a unique `idempotency_key`. Re-submitting the
same key returns `409 Conflict` — this is enforced both at the application
layer (pre-check) and at the database layer (unique constraint), so it holds
even under concurrent duplicate submissions.

## Error handling conventions

- `401` — missing/invalid/expired token.
- `403` — valid token, insufficient role (e.g. operator calling an
  admin-only endpoint).
- `404` — resource not found.
- `409` — conflict (duplicate camera code, duplicate watchlist identifier,
  duplicate event, invalid alert-state transition).
- `422` — validation failure (bad lat/lng, disabled camera reporting an
  event, missing identifier on an ANPR event, etc).

Error responses never include stack traces, stream credentials, or other
internal details — only a `detail` message.
